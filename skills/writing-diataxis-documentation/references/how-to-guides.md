# How-to guides

Need: help an already-competent practitioner achieve a real-world goal while
working.

- Start with the human goal or problem. Treat tools as means to that goal.
- Assume competence. Skip teaching and management of a learning experience.
- Give an executable, logically ordered route. Allow conditional branches and
  judgement because real work can't be fully controlled.
- Order steps around the user's activity and thinking. Avoid context switches
  and unresolved threads.
- The user owns adapting the guide and recovering from trouble. Prepare them for
  likely unexpected conditions.
- Prefer adaptability and practical usability to completeness.
- Keep explanation and reference catalogs out of the flow. Link them instead.
- Use a precise "How to ..." title. For troubleshooting, name the specific
  problem; skip topic labels.

## Language

- Open with the goal: "This guide shows you how to rotate credentials."
- Use conditional imperatives: "If you need zero downtime, roll one node at a
  time."
- Link complete options: "See the API reference for every option."

Reject a draft whose goal is merely "use feature X," whose scope is an
open-ended domain such as "build a web application," or whose primary purpose is
learning.
